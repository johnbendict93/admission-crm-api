## What this is

John (an Assistant Professor, currently on leave) is building an
Admission CRM to **sell to colleges and coaching centres** for managing
their student admission process — leads, applicants, applications, fees,
hostel, scholarships, telecaller/followup tracking, plus 10 ML-powered
features layered on top (conversion prediction, fraud detection, etc.).
Plan: finish the full product (backend + frontend + all ML) on synthetic
dev data first, demo-harden it, then do cold outreach to small coaching
centres for a free first pilot (no real student data or real pilot
customer exists yet). Delivery model: single-tenant — one private Render
+ Supabase deployment per customer, not multi-tenant SaaS.

There was an earlier Streamlit version of this app (still live at
admission-crm.streamlit.app, github.com/johnbendict93/Admission-CRM) —
that one is legacy/parallel, not what this handoff is about. **This
handoff is about the newer, hardened FastAPI + Next.js rebuild.**

## How to regenerate the typed client (only when the backend schema changes)

1. In the backend repo, in the `admission-crm-api` conda env:
   ```
   python -c "import json; from app.main import app; json.dump(app.openapi(), open('openapi.json', 'w'), indent=2)"
   ```
2. In `Admission-CRM-API/typed-client/`: `npm run generate` (uses `orval`,
   config at `orval.config.js`, reads `../openapi.json`).
3. Copy `typed-client/src/generated/` into
   `Admission-CRM-Frontend/src/lib/api-client/generated/` (overwrite, no
   need to delete first — same filenames get replaced in place).

**Gotcha:** `typed-client/node_modules/` and the frontend's own
`node_modules/` were `npm install`-ed on Windows. Running `npm run
generate` directly against them from the Linux `device_bash` VM fails
with an esbuild platform mismatch. Work around it by copying just the
`package.json`/`orval.config.js`/`src/` into a scratch folder outside the
mounted repo, `npm install` fresh there (gets Linux binaries), run
`orval` there, then copy only the `src/generated/` **output** back into
the real repos — never touch the real `node_modules` from the Linux side.

Both `openapi.json` and `typed-client/` are tracked in git now (they
weren't before — see commit `925912b`, found while starting this work).
Keep committing them when they change.

## Running everything locally (for live testing — guide John one step at a time)

Three separate terminals, in this order:
1. Backend: `conda activate admission-crm-api` → `cd Admission-CRM-API` →
   `uvicorn app.main:app --reload` (serves `http://127.0.0.1:8000`,
   talks to DEV Supabase — confirm `.env` has `ENVIRONMENT=development`).
2. Frontend: `cd Admission-CRM-Frontend` → `npm run dev` (serves
   `http://localhost:3000`).
3. Browser: `http://localhost:3000` → redirects to `/login` → sign in
   with a dev test account (env vars `TEST_ADMIN_EMAIL`/
   `TEST_ADMIN_PASSWORD` in the backend's `.env`, created via
   `scripts/create_test_users.py`).

**Gotcha already hit:** `uvicorn --reload` watches `.py` files, NOT
`.joblib` model files or other data — if you retrain a model, you must
manually stop (`Ctrl+C`) and restart `uvicorn`, a `--reload` auto-restart
won't pick it up. Also watch for John accidentally starting a *second*
`uvicorn` in a new terminal without stopping the old one — check which
terminal is actually still serving requests if a fix doesn't seem to
take effect.

## Standing rules (apply to ALL work on this project)

- **Dev-first.** Read-only on prod unless John explicitly says otherwise.
- **Golden Rule:** audit the real live schema/code before writing
  model/service/UI code — grep the actual files, don't guess field or
  hook names.
- **Cross-app impact check** before touching any shared table (the
  legacy Streamlit app and this FastAPI rebuild share some Supabase
  infrastructure history — check before assuming isolation).
- **Claude commits and shows the hash; John pushes himself** — his own
  PowerShell terminal has GitHub credentials, the Cowork device shell
  does not.
- **Never put secrets in chat or open `.env` files.**
- **Only synthetic/fake data** in dev — never real student data.
- **Communicate ONE STEP AT A TIME, in plain language, especially for
  multi-step technical work** — John gets confused easily. Don't dump 5
  commands at once; give one, wait for his pasted output, then the next.
- **Be honest/direct, not diplomatic** — especially about model quality,
  bugs, or scope gaps. If something is broken or incomplete, say so
  plainly rather than softening it.
- Ad hoc one-off audit/debug scripts use the `check_*.py` naming
  convention in the backend repo and are gitignored — never committed.
- `ml/eval/` (ground-truth files with live dev row ids) is also
  gitignored, never committed.
