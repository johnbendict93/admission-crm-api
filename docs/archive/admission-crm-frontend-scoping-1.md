# Admission CRM — Next.js Frontend Scoping Doc

Planning only — nothing scaffolded yet. This maps every backend module to a
frontend page, the exact generated hook each page calls, and the role gating
each page needs, then sequences the build.

## 0. Prerequisite already done: typed client

`Admission-CRM-API/typed-client/` now holds a generated TypeScript client —
types + TanStack Query v5 hooks for all 14 modules, generated by `orval` from
the live OpenAPI schema (`app.openapi()`, not a hand-maintained spec). Every
page below is built against these generated hooks, never a hand-typed
`fetch()` call. Regenerate with `npm run generate` inside that folder any
time the backend schema changes — never hand-edit anything under
`typed-client/src/generated/`.

## 1. Component / design system — decided once, here

**shadcn/ui + Tailwind CSS.** This is the standard pairing for a
Next.js + FastAPI stack and is decided at the project level, not per page:

- Tailwind for styling, shadcn/ui (Radix primitives + Tailwind, copied into
  the repo rather than installed as an opaque package) for the component
  layer — Table, Dialog, Form, Select, DatePicker, Badge, Tabs, Sidebar nav,
  Toast — all consistent by default, all editable in-repo since shadcn
  components live in your own `components/ui/` folder.
- TanStack Query v5 (already the target for the generated hooks) handles all
  server state — caching, refetch, optimistic updates on mutations.
- React Hook Form + Zod for every create/edit form, with Zod schemas
  generated or derived from the same OpenAPI types where practical, so form
  validation and API validation stay in sync.
- No separate state-management library (Redux/Zustand) needed at this
  scope — TanStack Query covers server state, and page-local UI state
  (open dialogs, selected filters) is plain `useState`.

## 2. Page / feature inventory — all 14 modules

Every module follows the same CRUD route shape:
`GET /{resource}` (paginated list), `GET /{resource}/{id}`,
`POST /{resource}`, `PATCH /{resource}/{id}`, `DELETE /{resource}/{id}`.
Role gating is identical across all 14 (from `app/core/jwt_auth.py`):
**read** = any authenticated role (admin/counselor/staff/viewer) — no
`viewer` block; **write** (create/update) = `require_writer`, blocks
`viewer` only; **delete** = `require_deleter`, admin/staff only.

## 3. Auth/session wiring (applies to every page above)

- `typed-client/src/api-mutator.ts`'s `getAccessToken()` placeholder needs
  to be replaced with the real session read once the Next.js app exists —
  likely a server-side helper reading an httpOnly cookie set at login,
  rather than client-side `localStorage` (avoids XSS token theft).
- Role-based UI gating (hide/disable write and delete controls for
  `viewer`, hide delete for non-admin/staff) should mirror the API's own
  enforcement — the API is the real gate; the UI gating is only to avoid
  showing controls that would 403, not a security boundary itself.
- A shared route wrapper/middleware checks for a valid session on every
  page except `/login`, matching the API's "every endpoint requires a
  bearer token except `/health`" posture.

## 4. Build order

**Phase A — Core admissions funnel** (highest business value, most
frequently used, and validates the whole stack — API client, auth, forms,
tables — before spending time on the rest):
1. Leads
2. Applications (depends on Applicants existing as a linked entity —
   build Applicants alongside/just before)
3. Fee Payments

**Phase B — Config/lookup screens** (low complexity, no dependencies on
Phase A being finished, good for filling in team velocity or parallelizing
across two people):
4. Document Types
5. Settings
6. Lookup Values

**Phase C — Remaining operational modules** (each follows the exact same
CRUD template proven in Phase A, so these should be fast once the pattern
is established):
7. Applicants (if not already pulled forward for Applications' FK)
8. Scholarships
9. Hostel Allotments
10. Telecallers
11. Call Schedules
12. Campus Visits
13. Followups
14. Counseling Sessions

**Phase D — Dashboard/reporting** (last, because it aggregates data from
everything above — building it earlier means rebuilding it as more
modules land):
15. Dashboard
16. Reports/export

## 6. Known gaps (found during the build, not resolved yet)

- **counselor_id on Counseling Sessions is a raw UUID text input, not a
  picker.** It's a required FK to `users(id)`, but no endpoint in this API
  exposes that table (no `/users` router exists - only `POST /auth/login`).
  `telecallers` was considered as a substitute source but is an unrelated
  table with its own id space, so it can't safely back this field. Revisit
  once a `GET /users` or `GET /staff` endpoint exists on the backend, then
  swap this for the same `<Select>` pattern used for applicant_id/lead_id
  elsewhere. Flagged inline in the UI in the meantime (Sept 2026).
